# Turning OWASP's catalog into reinhardt rules

OWASP publishes more than twenty "Top 10"-style lists, three verification standards, about 137 cheat sheets and a set of flagship tools, but only about eight of them are both current and code-level enough to drive a static scanner for vibe-coded apps: the **Top 10:2025** (web), **ASVS 5.0.0**, the **API Security Top 10 2023**, the **LLM Top 10 2026** (published 4 Aug 2026, which supersedes the 2025 list most tools still cite), the **Agentic Top 10 (Dec 2025)**, the **NHI Top 10 2025**, **Mobile Top 10 2024 with MASVS 2.1 / MASWE / MASTG**, and the **Cheat Sheet Series**, which now includes Next.js, JS/TS, "Secure Coding with AI" and MCP sheets. Several other lists are stale or never finished: Serverless (2018), Cloud-Native ("TBD"), Client-Side (still a 2022 "candidate list"), Privacy Risks (v2.0, repo archived March 2025) and ML (2023 draft). reinhardt should cite these as context, not as primary finding IDs. Build reinhardt in three layers. The first is a **versioned ID registry and crosswalk**: OWASP ships machine-readable data you can ingest (ASVS CSV/JSON, MASWE YAML front matter, nine mapping JSONs in the LLM 2026 release). The second is **agent guidance** distilled from the Proactive Controls and cheat sheets, used to triage heuristic findings and review what code cannot prove. The third is **deterministic rules**. The highest-yield rules are a small set of secrets-and-misconfiguration checks: Supabase `service_role` keys in client code, tables without RLS, open Firebase rules, `dangerouslyAllowBrowser: true` on LLM SDKs, string-built SQL, model output reaching `eval`/`innerHTML`, unverified JWTs, and iOS ATS/TLS bypasses. These map cleanly to OWASP IDs and have low false-positive rates. Business logic, insecure design, alerting, and whether an IDOR or RLS policy is actually exploitable stay with the agent or a human.

Three traps in this catalog are worth encoding as data-quality checks. The first is that **secondary sources are already wrong about the LLM 2026 list**. One news site printed invented names such as "Vector and Memory Flaws" and "Insecure Output Handling" and a wrong date. Only the canonical repo's `2026/final/*.md` should feed the registry ([LLM Top 10 repo](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10)). The second is that **ASVS 4.x IDs cannot be reused**: 5.0 completely restructured its chapters, so the password-length requirement that was V2.1.1 is now 6.2.1. The standard itself recommends version-prefixed IDs such as `v5.0.0-1.2.5` for exactly this reason ([ASVS 0x03](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x03-What-is-the-ASVS.md)). The third is that **the official texts contain typos**. Top 10 A03 lists "CWE-447 Use of Obsolete Function", but MITRE's ID is CWE-477. A07 mislabels CWE-298/299. Some MASTG beta tests point at an adjacent MASWE (test 0276, about the clipboard, names MASWE-0036 rather than MASWE-0030) ([A03 page](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A03_2025-Software_Supply_Chain_Failures.md), [MASTG-TEST-0276](https://github.com/OWASP/mastg/blob/master/tests-beta/ios/MASVS-PLATFORM/MASTG-TEST-0276.md)).

On the project side, OWASP's 15 Flagship projects include ASVS, the Top Ten, the Cheat Sheet Series, MAS, SAMM, WSTG, CycloneDX, Dependency-Check, Dependency-Track, DefectDojo, Juice Shop, CRS and Amass ([projects.json](https://github.com/OWASP/owasp.github.io/blob/main/_data/projects.json)). **ZAP is no longer an OWASP project.** It moved to the Linux Foundation's Software Security Project in August 2023 and became "ZAP by Checkmarx" in September 2024, still Apache-2.0 ([ZAP blog 2023](https://www.zaproxy.org/blog/2023-08-01-zap-is-joining-the-software-security-project/), [ZAP blog 2024](https://www.zaproxy.org/blog/2024-09-24-zap-has-joined-forces-with-checkmarx/)). For reinhardt, the tools matter as integration targets (CycloneDX for SBOM output, Dependency-Track and Dependency-Check rather than reimplementing SCA) and as test fixtures: **OWASP Benchmark** exists specifically to score SAST accuracy, and **Juice Shop** and **WrongSecrets** are known-vulnerable corpora for measuring precision and recall.

## The web core: Top 10:2025 sets categories, ASVS 5.0 sets requirements

### Top 10:2025 reorganized around root causes and added two categories

The 8th Top 10 draws on data from more than 2.8 million applications. It ranks categories by root cause rather than symptom, and each category averages about 25 CWEs ([Introduction](https://github.com/OWASP/Top10/blob/master/2025/docs/en/0x00_2025-Introduction.md)). Two changes affect reinhardt directly. **SSRF is now inside A01 Broken Access Control**, and **A03 Software Supply Chain Failures** widened the old "vulnerable components" item to cover build systems, IDEs and registries. A03 was the community survey's top-voted category and has the highest average exploit and impact scores.

| ID | Name | Key CWEs for reinhardt | What it absorbed or changed |
|---|---|---|---|
| A01:2025 | Broken Access Control | 862, 863, 639, 284, 918 (SSRF), 601, 22, 352, 1275, 922, 540 | Still #1; SSRF folded in; 40 CWEs |
| A02:2025 | Security Misconfiguration | 16, 611, 614, 1004, 942, 489, 547, 260 | Up from #5; now explicitly says no static keys in code, config or pipelines |
| A03:2025 | Software Supply Chain Failures | 1104, 1395, 1357, 477 | Expanded from A06:2021 |
| A04:2025 | Cryptographic Failures | 327, 338, 330, 321, 319, 916, 759, 347 | Down from #2; asks whether keys are checked into source |
| A05:2025 | Injection | 89, 78, 79, 94, 95, 113, 116, 917 | Includes XSS; points to LLM01 for prompt injection |
| A06:2025 | Insecure Design | 434, 602, 807, 799, 598, 362, 1021, 1022 | Design gaps and business logic |
| A07:2025 | Authentication Failures | 798, 259, 287, 307, 384, 521, 613, 295, 1392 | Renamed; adds "validate JWT `aud`, `iss` and scopes" |
| A08:2025 | Software or Data Integrity Failures | 502, 829, 830, 915, 494, 565 | Untrusted code/data treated as trusted; mass assignment (CWE-915) |
| A09:2025 | Security Logging & Alerting Failures | 532, 117, 778 | Renamed to stress alerting; "incredibly difficult to test for" |
| A10:2025 | Mishandling of Exceptional Conditions | 209, 636, 390, 391, 248, 252, 476, 754, 756 | **New**: failing open, swallowed errors |

Sources: [A01](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A01_2025-Broken_Access_Control.md), [A02](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A02_2025-Security_Misconfiguration.md), [A03](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A03_2025-Software_Supply_Chain_Failures.md), [A04](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A04_2025-Cryptographic_Failures.md), [A05](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A05_2025-Injection.md), [A06](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A06_2025-Insecure_Design.md), [A07](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A07_2025-Authentication_Failures.md), [A08](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A08_2025-Software_or_Data_Integrity_Failures.md), [A09](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A09_2025-Security_Logging_and_Alerting_Failures.md), [A10](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A10_2025-Mishandling_of_Exceptional_Conditions.md).

The 2025 text gives reinhardt explicit grounds for its core checks. A01 says access control is effective only in **"trusted server-side code or serverless APIs"**, which is the basis for flagging client-only role checks and client-exposed service keys. A02, A03 and A04 each condemn secrets in code ([A01](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A01_2025-Broken_Access_Control.md), [A02](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A02_2025-Security_Misconfiguration.md)). A10 is especially useful for AI-generated code, which habitually swallows errors. It names "failing open" (CWE-636) and recommends "code review or static analysis" as a prevention ([A10](https://github.com/OWASP/Top10/blob/master/2025/docs/en/A10_2025-Mishandling_of_Exceptional_Conditions.md)). None of the Top 10:2025 pages mention AI-generated code. The only AI references are the LLM cross-reference in A05 and AI-assisted alerting in A09.

### ASVS 5.0 gives every finding a precise, version-pinned requirement

ASVS 5.0.0 (May 2025) has 17 chapters: V1 Encoding and Sanitization, V2 Validation and Business Logic, V3 Web Frontend Security, V4 API and Web Service, V5 File Handling, V6 Authentication, V7 Session Management, V8 Authorization, V9 Self-contained Tokens, V10 OAuth and OIDC, V11 Cryptography, V12 Secure Communication, V13 Configuration, V14 Data Protection, V15 Secure Coding and Architecture, V16 Security Logging and Error Handling, and V17 WebRTC ([ASVS 5.0/en](https://github.com/OWASP/ASVS/tree/master/5.0/en)). **L1 is about 20% of requirements, and the standard itself suggests that "an early-stage startup" may focus on Level 1** ([0x03](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x03-What-is-the-ASVS.md)). That fits reinhardt's audience of individual builders, so make **L1 the default profile**.

These statically checkable L1 requirements should anchor reinhardt's rules. **1.2.4** parameterized queries; **1.3.2** no `eval()` or dynamic code execution; **2.2.2** validation enforced server-side, because client validation is not a security control; **3.2.2** `textContent` for text; **3.3.1** cookies carry `Secure` and a `__Host-`/`__Secure-` prefix; **3.4.1** HSTS of at least one year; **3.4.2** a fixed or allowlisted CORS origin; **5.2.1/5.2.2** upload size limits plus extension and magic-byte checks; **5.3.2** server-generated file paths; **6.2.1** passwords of at least 8 characters (15 recommended); **6.3.1** brute-force controls; **6.3.2** no default accounts; **7.2.1/7.2.4** backend token verification and a new token at login; **8.2.2** data-level authorization (IDOR); **8.3.1** authorization at a trusted layer; **9.1.1/9.1.2/9.2.1** verify the JWT signature, allowlist algorithms (never `None`), and enforce `exp`/`nbf`; **11.3.1/11.4.1** no ECB and no MD5; **12.2.1** TLS everywhere; **13.4.1** no `.git` deployed; **14.2.1** no secrets in URLs; and **15.3.1** return only required fields ([ASVS chapters](https://github.com/OWASP/ASVS/tree/master/5.0/en)). There is one gap to design around: **V13 secret management and V16 logging have no L1 requirements** in 5.0.0. Secrets-in-code findings should therefore carry Top 10/NHI tags plus an ASVS L2 reference, not an L1 claim.

### Proactive Controls 2024 supplies the remediation vocabulary

The ten developer-facing controls are C1 Implement Access Control, C2 Use Cryptography to Protect Data, C3 Validate all Input & Handle Exceptions, C4 Address Security from the Start, C5 Secure By Default Configurations, C6 Keep your Components Secure, C7 Secure Digital Identities, C8 Leverage Browser Security Features, C9 Implement Security Logging and Monitoring, and **C10 Stop Server Side Request Forgery**, which is new compared with 2018. The project is licensed **CC BY-SA 4.0** ([Proactive Controls repo](https://github.com/OWASP/www-project-proactive-controls)). Because they are phrased as things to *do*, the controls make the best skeleton for reinhardt's fix-it messages and for an agent rules file. Use the "Vulnerabilities Prevented" section of each control as the authoritative C→Top 10 mapping rather than a hand-built one. The research did not extract that section.

## Backend, secrets and pipelines: API, NHI and CI/CD lists cover what vibe-coded apps actually ship

Vibe-coded apps are mostly thin API layers over a BaaS, so the **API Security Top 10 2023** maps more directly to their findings than the web list does. Its items are API1 Broken Object Level Authorization, API2 Broken Authentication, API3 Broken Object Property Level Authorization (excessive data exposure merged with mass assignment), API4 Unrestricted Resource Consumption, API5 Broken Function Level Authorization, API6 Unrestricted Access to Sensitive Business Flows, API7 SSRF, API8 Security Misconfiguration, API9 Improper Inventory Management, and API10 Unsafe Consumption of APIs ([OWASP API Top 10](https://owasp.org/API-Security/editions/2023/en/0x11-t10/)). Two passages carry most of the weight for AI wrappers. API4 explicitly covers **paid per-request integrations** and says to "configure spending limits for all service providers/API integrations". API2 says "API keys should not be used for user authentication" ([API repo](https://github.com/OWASP/API-Security/tree/master/editions/2023/en)).

The **NHI Top 10 2025** is the list most directly aligned with secret scanning. Its items are NHI1 Improper Offboarding, NHI2 Secret Leakage, NHI3 Vulnerable Third-Party NHI (including IDE extensions), NHI4 Insecure Authentication, NHI5 Overprivileged NHI, NHI6 Insecure Cloud Deployment Configurations (static credentials or poorly constrained OIDC in CI/CD), NHI7 Long-Lived Secrets, NHI8 Environment Isolation, NHI9 NHI Reuse, and NHI10 Human Use of NHI ([NHI Top 10](https://owasp.org/www-project-non-human-identities-top-10/)). NHI2, NHI5, NHI6, NHI7 and NHI8 can all be detected from a repository: the same key in `.env.development` and `.env.production`, `service_role` used where the publishable key would do, and static `AWS_ACCESS_KEY_ID` in workflows instead of OIDC. NHI1 and NHI10 cannot.

Severity must depend on the key type, not just on finding a match. Vendor documentation establishes which prefixes are safe to expose: Stripe `pk_live_`/`pk_test_` are publishable, while `sk_`/`rk_` are secret ([Stripe Docs](https://docs.stripe.com/keys)). Supabase `sb_publishable_` and legacy `anon` are safe; **`sb_secret_` and `service_role` carry BYPASSRLS**; and Supabase is deprecating the legacy JWT keys by the end of 2026 ([Supabase API keys](https://supabase.com/docs/guides/api/api-keys)). AWS `AKIA` keys are long-lived, while `ASIA` keys are temporary STS credentials ([AWS IAM](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_identifiers.html)). GitHub tokens (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`) end in a CRC32 checksum that can be validated offline, which cuts false positives below the roughly 0.5% that prefix matching alone produces ([GitHub blog](https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/)). Gitleaks' default config is a practical regex source for Anthropic (`sk-ant-api03-…AA`), OpenAI (the `T3BlbkFJ` marker), Google `AIza` and others ([gitleaks.toml](https://raw.githubusercontent.com/gitleaks/gitleaks/master/config/gitleaks.toml)). The Anthropic and OpenAI formats were not confirmed against vendor documentation, so treat them as tool heuristics.

The **CI/CD Top 10 (v1.0, 2022)** has not been updated but is still the canonical taxonomy: CICD-SEC-1 Insufficient Flow Control, -2 Inadequate IAM, -3 Dependency Chain Abuse, -4 Poisoned Pipeline Execution, -5 Insufficient PBAC, -6 Insufficient Credential Hygiene, -7 Insecure System Configuration, -8 Ungoverned 3rd-Party Services, -9 Improper Artifact Integrity Validation, and -10 Insufficient Logging ([CI/CD Top 10](https://owasp.org/www-project-top-10-ci-cd-security-risks/)). GitHub's own hardening guide supplies the concrete rules. **Pinning an action to a full-length commit SHA is "the only way to use an action as an immutable release."** `pull_request_target` workflows "must not explicitly check out untrusted code." Untrusted contexts such as `github.event.pull_request.title` must not be interpolated into `run:` steps ([GitHub Docs](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)). For containers, the Docker Security Cheat Sheet's RULE #0–#13 (set a `USER`, never `--privileged`, never mount `docker.sock`, bind ports to `127.0.0.1`) and Kubernetes 2025 K01/K03 cover Dockerfile and manifest checks ([Docker CS](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html), [K01 2025](https://github.com/OWASP/www-project-kubernetes-top-ten/blob/main/2025/en/src/K01-Insecure-Workload-Configurations.md)). These are lower priority for reinhardt's audience.

## The AI layer: key everything to LLM 2026 and the Agentic Top 10

**The LLM Top 10 2026 is the current list**, published 4 August 2026 (the landing page says 3 August; the canonical repo says 4 August). It reorders the 2025 list and renames one entry:

Source: [GenAI-LLM-Top10 repo](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10).

Three features of the 2026 release matter for reinhardt. First, it **ships machine-readable mappings** (`asi-2026.json`, `cwe-4.20.json`, MITRE ATLAS and ATT&CK, NIST AI RMF and others) in `2026/final/mappings/`, which can be imported into the crosswalk directly ([2026/final](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/tree/main/2026/final)). Second, its primary CWEs give each rule a stable anchor: LLM01 → **CWE-1427**, LLM07 and LLM10 → **CWE-1426**, LLM06 → CWE-400/770, and LLM02 → CWE-200/359/532 ([Appendix A](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/Appendix_A_Related_Framework_Mappings.md)). Third, it **draws scope lines that change which ID applies**. LLM08 Hidden Context Exposure explicitly excludes "client-side bundle inspection", so an API key in a browser bundle maps to LLM02 plus CWE-798, not LLM08. A secret embedded in a system prompt is LLM08 at "high" severity ([LLM08](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM08_HiddenContextExposure.md)). The preface sets a further boundary: once the model "becomes an actor, with tools… memory", the risk belongs to the Agentic Top 10 ([Preface](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM00_Preface.md)).

The 2026 entries are unusually concrete, which suits static rules. LLM10 now explicitly "spans the insecure code that assistants generate at scale". It also adds **Markdown image and link-preview exfiltration** and ANSI escape injection, and recommends disabling auto-rendering of Markdown images by default ([LLM10](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM10_ImproperOutputHandling.md)). LLM03 says to "avoid the use of open-ended tools… (e.g., run a shell command, fetch a URL)" and that tools "should define a strict schema" ([LLM03](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md)). LLM06 states that request-rate limiting "alone is no longer sufficient" and calls for token-aware caps, hard spending limits and agent circuit breakers ("step limits, recursion depth limits, time limits, and per-run cost ceilings") ([LLM06](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM06_UnboundedConsumption.md)). LLM01 says to "pin, sign, and verify every MCP server" and to strip invisible Unicode ([LLM01](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM01_PromptInjection.md)). The SDKs themselves supply a near-zero-false-positive signal: both the OpenAI and Anthropic JS SDKs refuse to run in browsers unless `dangerouslyAllowBrowser: true` is set, and both warn that doing so exposes the secret key ([openai-node](https://github.com/openai/openai-node), [anthropic-sdk-typescript](https://github.com/anthropics/anthropic-sdk-typescript)).

The **Agentic Top 10** (released 9 Dec 2025) uses these canonical titles: ASI01 Agent Goal Hijack, ASI02 Tool Misuse & Exploitation, ASI03 Identity & Privilege Abuse, ASI04 Agentic Supply Chain Vulnerabilities, ASI05 Unexpected Code Execution (RCE), ASI06 Memory & Context Poisoning, ASI07 Insecure Inter-Agent Communication, ASI08 Cascading Failures, ASI09 Human-Agent Trust Exploitation, and ASI10 Rogue Agents ([asi-2026.json](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/mappings/asi-2026.json)). Its guiding principle is "least agency" ([Giskard](https://www.giskard.ai/knowledge/owasp-top-10-for-agentic-application-2026)). The PDF itself was not read, so the per-item mitigation text in the research comes from secondary summaries. ASI02–ASI06 can be detected in code (tool definitions, MCP configs, memory writes). ASI07–ASI10 are architectural. The earlier **Agentic Threats & Mitigations guide** (17 Feb 2025, T1–T15) is the precursor taxonomy and does not need its own tag ([genai.owasp.org](https://genai.owasp.org/resource/agentic-ai-threats-and-mitigations/)). The **ML Top 10 (2023 draft)** matters only for ML06 (unpinned model downloads, pickle loading) ([ML Top 10](https://owasp.org/www-project-machine-learning-security-top-10/)). The **AI Exchange** (owaspai.org) contributes named controls such as `#LEASTMODELPRIVILEGE`, `#INPUTSEGREGATION` and `#ENCODEMODELOUTPUT`, plus the "lethal trifecta" framing (attacker data, sensitive access, exfiltration path), which makes good agent-guidance vocabulary ([owaspai.org overview](https://owaspai.org/docs/ai_security_overview/)). Those control spellings came through a summarizer and should be spot-checked.

## iOS: chain every finding from MASTG test to Mobile Top 10

The **Mobile Top 10 2024** items are M1 Improper Credential Usage, M2 Inadequate Supply Chain Security, M3 Insecure Authentication/Authorization, M4 Insufficient Input/Output Validation, M5 Insecure Communication, M6 Inadequate Privacy Controls, M7 Insufficient Binary Protections, M8 Security Misconfiguration, M9 Insecure Data Storage, and M10 Insufficient Cryptography ([Mobile Top 10 index](https://github.com/OWASP/www-project-mobile-top-10/blob/master/index.md)). Prefix the IDs with the year. The 2016 list reused the same numbers for different risks (2016's M2 was Insecure Data Storage), so bare `M2` is ambiguous. "Hardcoded Secrets" did not make the 2024 list as its own entry, but M1's prevention text covers it.

**MASVS v2.1.0** (18 Jan 2024) has 8 groups and 24 controls. v2.0 dropped L1/L2/R levels in favor of MAS profiles, and v2.1 added **MASVS-PRIVACY-1..4** (minimize access, prevent identification, be transparent, give users control) ([MASVS yaml](https://github.com/OWASP/masvs/blob/master/OWASP_MASVS.yaml)). The other groups are STORAGE-1/2, CRYPTO-1/2, AUTH-1/2/3, NETWORK-1/2, PLATFORM-1/2/3, CODE-1..4 and RESILIENCE-1..4. The part a scanner should build on is **MASWE**. It has 78 weaknesses (MASWE-0001 to MASWE-0078), each with YAML front matter carrying `masvs-v2` and `cwe` mappings, and MASTG tests reference them through a `maswe:` key ([MASWE-0005](https://github.com/OWASP/maswe/blob/main/weaknesses/MASVS-STORAGE/MASWE-0005.md), [MASTG-TEST-0396](https://github.com/OWASP/mastg/blob/master/tests-beta/ios/MASVS-NETWORK/MASTG-TEST-0396.md)). The resulting chain, **MASTG-TEST → MASWE → MASVS → Mobile Top 10**, is machine-readable except for the last hop. OWASP publishes no MASWE→Top 10 mapping, so label that link "inferred."

Nearly every iOS signal reinhardt needs has a dedicated MASTG test. These include ATS cleartext keys such as `NSAllowsArbitraryLoads` and `NSExceptionAllowsInsecureHTTPLoads` (TEST-0322); weak TLS exceptions (0342); hardcoded `http://` URLs (0321); `URLSessionDelegate` challenge handlers that call `.useCredential` without `SecTrustEvaluateWithError` (0396, which OWASP itself flags as a heuristic for manual review); `UserDefaults` and other unencrypted private storage (0300); logging through `print`/`NSLog` (0297); `CC_MD5`/`Insecure.SHA1` (0211); `rand()`/`random()` for security values (0311, where `arc4random` is acceptable); `UIPasteboard.general` writes (0276); WKWebView native bridges (0376); and custom URL scheme handlers without input or source validation (0370/0371) ([MASTG iOS tests](https://github.com/OWASP/mastg/tree/master/tests-beta/ios)). **React Native and Expo have no MASTG coverage**, so their rules rest on vendor docs. RN calls AsyncStorage "an unencrypted key-value store" unfit for tokens ([React Native Security](https://reactnative.dev/docs/security)), and Expo warns that `EXPO_PUBLIC_` values are "visible in plain-text in your compiled application" ([Expo env vars](https://docs.expo.dev/guides/environment-variables/)). One Apple rule, not an OWASP one, is a hard App Store gate that fits reinhardt's privacy angle: **since 1 May 2024, apps that use required-reason APIs without declaring them in `PrivacyInfo.xcprivacy` are rejected** ([Apple](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api)). MASWE-0073/0074 and MASTG-TEST-0281 (undeclared tracking domains) give it an OWASP anchor ([MASTG-TEST-0281](https://github.com/OWASP/mastg/blob/master/tests-beta/ios/MASVS-PRIVACY/MASTG-TEST-0281.md)).

## Privacy and the long tail: frozen lists that still justify reinhardt's core check

For reinhardt's privacy-drift check, OWASP's most useful privacy material is the frozen **Top 10 Privacy Risks v2.0 (2021)** combined with two cheat sheets. The list is P1 Web Application Vulnerabilities, P2 Operator-sided Data Leakage, P3 Insufficient Data Breach Response, P4 Consent on Everything, P5 Non-transparent Policies, Terms and Conditions, P6 Insufficient Deletion of User Data, P7 Insufficient Data Quality, P8 Missing or Insufficient Session Expiration, P9 Inability of Users to Access and Modify Data, and P10 Collection of Data Not Required for the User-Consented Purpose ([Privacy Top 10](https://owasp.org/www-project-top-10-privacy-risks/), [tab_topprivacy.md](https://raw.githubusercontent.com/OWASP/www-project-top-10-privacy-risks/master/tab_topprivacy.md)). No item is literally titled third-party sharing. **The "SDK in code but not named in the privacy policy" finding belongs under P5**, supported by P4 and P10 and by the User Privacy Protection cheat sheet's "Honesty & Transparency" item: disclose data collection and external requests before users commit ([User Privacy CS](https://cheatsheetseries.owasp.org/cheatsheets/User_Privacy_Protection_Cheat_Sheet.html)). The Logging cheat sheet supplies an explicit do-not-log list (session IDs, access tokens, PII, passwords, connection strings, keys, card data, and data the user opted out of) along with a retention rule ([Logging CS](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). OWASP has no consent-management cheat sheet and no iOS ATT guidance outside MASVS-PRIVACY.

The remaining lists are useful as secondary tags or as rationale. The **Client-Side Top 10** (candidate list) names "Sensitive Data Leakage" (trackers and pixels), "JavaScript Drift", "Sensitive Data Stored Client-Side" and "Not Using Standard Browser Security Controls" (CSP, SRI, iframe sandboxes). It has no official ID prefix, so cite it by number and name and don't invent "CSR-" IDs ([Client-Side Top 10](https://owasp.org/www-project-top-10-client-side-security-risks/)). The **Citizen Development Top 10** (the 2025 rebrand of LCNC) adds **CD-SEC-01 Blind Trust**, and its CD-SEC-04 explicitly lists "AI assistants processing raw support logs containing credentials" and data flows "crossing organizational boundaries". That is a close conceptual match for vibe-coded apps ([CD-SEC-04](https://owasp.github.io/www-project-citizen-development-top10-security-risks/content/2022/en/CD-SEC-04-Sensitive-Data-Leakage-and-Handling-Failures)). The **Business Logic Abuse Top 10 (2025)** provides secondary tags for mass assignment (BLA3 Object State Manipulations), missing rate limits (BLA7), user enumeration (BLA8) and leftover test endpoints (BLA10 Shadow Function Abuse). Its names changed between the June 2025 press release and the repo, so use the repo ([tab_top10.md](https://raw.githubusercontent.com/OWASP/www-project-top-10-for-business-logic-abuse/main/tab_top10.md)). The **Desktop Top 10 (2021)** is out of scope.

The **Cheat Sheet Series** is the richest source of rule rationale. Its 137 sheets now include a **Next.js Security** sheet, which says to treat each Server Action as "a client-callable POST entry point", not to make middleware/proxy "the only authorization layer" (citing CVE-2025-29927), and to use `NEXT_PUBLIC_` "only when its value is intentionally public" ([Next.js CS](https://cheatsheetseries.owasp.org/cheatsheets/Nextjs_Security_Cheat_Sheet.html)). It also has a **Secure Coding with AI** sheet covering hallucinated dependencies, rules files, and Markdown/Unicode injection ([Secure Coding with AI CS](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Coding_with_AI_Cheat_Sheet.html)), and an **NPM Security** sheet that names slopsquatting directly: AI assistants "may hallucinate package names that do not actually exist" ([NPM CS](https://cheatsheetseries.owasp.org/cheatsheets/NPM_Security_Cheat_Sheet.html)). The Session sheet's warning is unambiguous: "Do not store authentication tokens, session IDs, JWTs, refresh tokens, or any credential in `localStorage` or `sessionStorage`" ([Session CS](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). The Password Storage sheet gives numeric thresholds a rule can enforce: Argon2id m=19 MiB/t=2, bcrypt work factor of at least 10, PBKDF2-SHA256 with at least 600,000 iterations ([Password Storage CS](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)). Two sheets should not be used: Transport Layer Protection is deprecated in favor of Transport Layer Security, and Abuse Case is archived. **No OWASP sheet covers Supabase or Firebase.** RLS appears only as generic Postgres in Multi-Tenant Security ([Multi-Tenant CS](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)). Reinhardt's BaaS rules must cite vendor docs: "Enable RLS on every table in an exposed schema" ([Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)) and Firebase's insecure-rules guide ([Firebase](https://firebase.google.com/docs/rules/insecure-rules)). Map them to OWASP IDs through A01/API1.

## How to distill: registry, agent guidance, deterministic rules

**Knowledge layer.** Store a versioned registry keyed by canonical ID, with aliases and edges. Suggested fields per rule: `owasp_top10_2025`, `asvs_5` (`v5.0.0-x.y.z`), `api_2023`, `llm_2026` with a `llm_2025` alias, `asi`, `nhi_2025`, `cicd`, `mobile_2024`, `masvs`, `maswe`, `mastg`, `privacy_v2`, `cwe`, `proactive_2024`, `detectability` (static / heuristic / agent / human), `platforms`, and `vendor_refs` for Supabase, Firebase, Apple and Expo facts. Where OWASP provides the data, ingest it instead of transcribing it: ASVS CSV/JSON, MASWE front matter, MASTG `maswe:` keys, and the LLM 2026 `mappings/*.json` ([ASVS README](https://github.com/OWASP/ASVS), [MASWE](https://github.com/OWASP/maswe/tree/main/weaknesses), [LLM 2026 final](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/tree/main/2026/final)). Mark every hand-made crosswalk edge, such as MASWE→Mobile Top 10 or the Proactive C→Top 10 links, as `inferred`. Check licensing before quoting text verbatim. Proactive Controls is CC BY-SA 4.0, which is share-alike. The licenses of the other projects were not verified, so paraphrase and link unless a project's LICENSE confirms otherwise.

**Agent guidance layer.** reinhardt is an open-source agent harness that targets Codex first, so the OWASP material that cannot become a regex should become instructions. One part is an `AGENTS.md`-style rules file built from the Proactive Controls and the GenAI "build the system around [the model], so that when the model is fooled… nothing important breaks" principle ([Preface](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM00_Preface.md)). The rest are triage prompts for each heuristic rule, for example "Is this `.eq('id', param)` scoped to the session user anywhere upstream?". The Secure Coding with AI sheet treats rules files themselves as an attack surface ([Secure Coding with AI CS](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Coding_with_AI_Cheat_Sheet.html)). reinhardt should therefore also scan the user's own `.cursorrules`, `AGENTS.md` and MCP configs.

**Deterministic layer.** The prioritized list below is ordered by impact multiplied by precision. P0 rules are high-confidence and critical, and should fail CI. P1 rules are high-value checks that need some data-flow or heuristic context and should be surfaced with agent triage. P2 rules are privacy, mobile and infrastructure checks that complete coverage.

**What must stay with the agent or a human.** Some risks cannot be decided from source: whether the design is right (A06, Proactive C4), abuse of business flows such as checkout or invite spam (API6, most BLA items), the combined runtime behavior of several RLS policies or Firebase rules, actual IDOR exploitability across upstream middleware, alerting and monitoring (A09 says it is "incredibly difficult to test for"), breach response and data quality (P3, P7), MFA and breached-password checks, deployed headers and cloud IAM without IaC, NHI offboarding and human use of NHIs (NHI1, NHI10), SCM settings and pipeline logging (CICD-SEC-7, -10), inter-agent trust and rogue-agent behavior (ASI07–ASI10), prompt-injection robustness and misinformation (LLM01 and LLM07 beyond structural signals), and whether a privacy policy semantically covers a detected SDK. reinhardt's agent layer should handle these by reading the code and policy around a flagged location and stating its confidence. Statically detectable is not the same as statically certain.

## Conclusion

OWASP's catalog is far broader than any single scanner can use, but for vibe-coded apps the useful material reduces to two ideas. The first is that **authority belongs on the server and secrets belong off the client**. That one principle underlies A01, API1/3/5, NHI2, LLM02/08, M1 and MASWE-0004, and it explains why Supabase/Firebase misconfiguration and client-exposed keys outrank classic injection in reinhardt's priority list. These apps fail most often through BaaS defaults and env-var naming, not through hand-written SQL. The second is that **model output is untrusted input**. The 2026 LLM list makes this explicit by extending Improper Output Handling to the code assistants generate, which places reinhardt's own target, AI-written apps, inside OWASP's scope for the first time.

Two strategic implications follow. Tagging against **LLM 2026, Top 10:2025 and ASVS v5.0.0 from day one** is a cheap differentiator, because most existing tooling and blog content still cites the 2025 LLM list and ASVS 4.x IDs, and secondary sources have already published wrong 2026 names. And since **no OWASP document covers Supabase, Firebase, Expo or Apple's privacy manifest**, reinhardt's vendor-specific rules are also where it can add original knowledge rather than repackage OWASP. Those rules should carry vendor citations alongside OWASP IDs and be benchmarked against OWASP Benchmark, Juice Shop and WrongSecrets, so that claims of precision rest on measured results.
